# Panel de administración para Encuentrame

El cambio agrega un panel de administración completo bajo `/admin`: middleware de protección, seis server actions con validación de rol, layout con sidebar oscuro, y cuatro páginas (dashboard de métricas, tabla de negocios con toggles, tabla de usuarios con cambio de rol, y grid de categorías con conteos). La arquitectura replica el patrón del dashboard de propietarios: server components para la carga de datos, client components ligeros para las acciones interactivas.

Watch for: el server action `changeUserRole` no impide que un admin se degrade a sí mismo — posible bloqueo accidental de acceso (confirmed). El optimistic update en `ChangeRoleButton` no sincroniza el badge de rol en la misma fila, solo actualiza el texto del botón (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

El middleware en `updateSession` guarda `/admin/*` correctamente: redirige a `/auth/login` si no hay sesión y a `/` si el rol no es `admin`. El layout duplica esa misma verificación, lo cual es una capa adicional de defensa correcta dado que el middleware corre en Edge runtime con acceso limitado.

Cada server action pasa por `getAdminUser()` antes de tocar la base de datos, lo que centraliza la verificación de rol. El patrón es sólido, pero `changeUserRole` acepta `newRole: 'user' | 'owner'` sin verificar que `userId !== user.id`, lo que permite que el único superadmin se degrade a sí mismo.

Los client components `ToggleBusinessButton` y `ChangeRoleButton` implementan optimistic UI con reversión en catch. Sin embargo, el server action `toggleBusinessActive` / `toggleBusinessVerified` retorna `void | { error: string }` — cuando hay error, el `await` en el client component no lanza una excepción, sino que resuelve con `{ error }`. El bloque `catch` nunca se activa y el optimistic update queda sin revertir.

La página de categorías es read-only como se especificó. Todas las páginas tienen `export const instant = false` y todo el texto de UI está en español.

<summary>Issues (3)</summary>

1. **Auto-degradación de admin** — `changeUserRole` no verifica que `userId !== currentUser.id`. Un admin puede cambiarse el rol a `user` u `owner`, bloqueándose el acceso al panel. Agregar un guard: `if (userId === user.id) return { error: 'No puedes cambiar tu propio rol' }`.

2. **Optimistic revert silencioso en toggle buttons** — `toggleBusinessActive` y `toggleBusinessVerified` retornan `{ error: string }` en fallo, no lanzan una excepción. El `try/catch` en `ToggleBusinessButton` y `ChangeRoleButton` nunca entra al `catch` cuando el action falla, por lo que el estado optimista queda incorrecto. Cambiar el patrón a: inspeccionar el valor de retorno del action y revertir si contiene `error`, o hacer que el action lance en caso de error.

3. **Badge de rol no actualiza tras cambio** — `ChangeRoleButton` solo actualiza `optimisticRole` (el texto del botón). El badge de rol que se renderiza en el server component queda desactualizado hasta que `revalidatePath` fuerza el rerender. No es un bug de correctitud — la data es eventualmente consistente — pero el usuario verá el badge en el valor viejo mientras el botón ya muestra el nuevo rol. Considerar pasar el badge como estado local también, o aceptarlo como limitación conocida de la arquitectura server/client.

<summary>Details</summary>

### Auto-degradación de admin en changeUserRole

`changeUserRole` recibe `userId: string` y `newRole: 'user' | 'owner'`. No hay verificación de que `userId !== user.id`. Un admin autenticado puede llamar esta acción con su propio ID y degradarse. Dado que el middleware y el layout bloquean el acceso a no-admins, esto equivale a un auto-lock-out. El fix es un guard antes del update:

```ts
if (userId === user.id) return { error: 'No puedes cambiar tu propio rol' }
```

Confirmado en `src/app/actions/admin.ts` líneas 96-108.

### Optimistic revert que nunca dispara

Ambos botones client tienen este patrón:

```ts
try {
  await toggleBusinessActive(businessId)
} catch {
  setOptimistic((prev) => !prev) // revert
}
```

El server action tiene firma `Promise<void | { error: string }>`. Cuando falla, retorna `{ error }` — no lanza. El `await` resuelve normalmente, el `catch` no se ejecuta, y el estado optimista permanece invertido aunque la operación falló. El usuario verá el botón en estado incorrecto hasta que recargue la página.

El mismo problema afecta a `ChangeRoleButton`. La corrección mínima:

```ts
const result = await toggleBusinessActive(businessId)
if (result && 'error' in result) {
  setOptimistic((prev) => !prev) // revert
}
```
